# Acoustic Trust Synthesis Pipeline — Design Spec

## Core Framing

Acoustic detection is a noisy sensor contributing evidence into a trust synthesis pipeline. It is not automatic event creation.

```
acoustic_signals  →  synthesis pipeline  →  public_events
(raw sensor data)     (clustering, scoring,    (map-visible,
                       weighting, anti-spoof)   confirmed, trusted)
```

No single sensor type independently generates CRITICAL public alerts. A detection on one device is evidence. Evidence accumulates. Events emerge from evidence through a deliberate synthesis process.

---

## Signal vs Event — Separation of Concerns

### `acoustic_signals` table (new)

Acoustic detections write to `acoustic_signals`, not to `public_events` or the existing `reports` table.

```sql
CREATE TABLE acoustic_signals (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    client_id     TEXT NOT NULL,           -- UUIDv7 generated by client, unique index with 10min TTL window
    pubkey        TEXT NOT NULL,           -- authenticated Nostr pubkey
    threat_class  TEXT NOT NULL,
    confidence    FLOAT4 NOT NULL,        -- mean confidence across frames in this window
    confidence_variance FLOAT4,          -- variance across frames; high variance = disagreement within window
    lat           FLOAT8 NOT NULL,
    lng           FLOAT8 NOT NULL,
    h3_r9         TEXT NOT NULL,           -- H3 cell at resolution 9 (~0.1km²), computed server-side
    h3_r7         TEXT NOT NULL,           -- H3 cell at resolution 7 (~5km²), for cluster grouping
    received_at   TIMESTAMPTZ NOT NULL DEFAULT now(),

    -- coordinate precision: exact coords retained transiently, coarsened on schedule (see Privacy section)
    -- lat/lng: nulled after 24h via scheduled job
    -- h3_r9: retained 7 days, then nulled
    -- h3_r7: retained indefinitely (lowest precision)

    -- model governance
    model_version      TEXT NOT NULL,
    threshold_profile  TEXT NOT NULL,
    inference_backend  TEXT NOT NULL,      -- 'webgl' | 'wasm' | 'cpu'
    processing_latency INT,               -- ms
    dropped_frames     INT NOT NULL DEFAULT 0,
    device_category    TEXT,              -- 'mobile' | 'desktop' | 'tablet'

    -- anti-spoofing inputs
    signal_fingerprint TEXT,              -- sha256 of normalised waveform embedding
    trust_state   TEXT NOT NULL DEFAULT 'pending'
                  CHECK (trust_state IN ('pending', 'corroborating', 'confirmed', 'disputed', 'expired'))
);

CREATE UNIQUE INDEX acoustic_signals_client_id_dedup
    ON acoustic_signals (client_id)
    WHERE received_at > now() - INTERVAL '10 minutes';
```

H3 cells are computed server-side from client-supplied `lat`/`lng`. The client never supplies cell IDs.

### Trust state machine

```
pending  ──corroboration arrives──►  corroborating  ──quorum reached──►  confirmed
  │                                                                           │
  ├──anti-spoof flag / moderator──►  disputed  ◄──moderator demote──────────┘
  │
  └──no corroboration within TTL──►  expired
```

- `pending`: a single signal received, below corroboration threshold. Not visible on public map. Visible locally at low opacity (see Soft Visibility).
- `corroborating`: 2+ distinct pubkeys in same H3 r9 cell within 120s. Still below quorum. Soft-visible to nearby users.
- `confirmed`: weighted corroboration score meets threshold (see Scoring). Published to public map.
- `disputed`: flagged by anti-spoofing heuristics or moderator review. Pulled from map pending investigation. Can be re-confirmed only by moderator action.
- `expired`: `pending` signals with no corroboration within 5 minutes. Retained in DB for forensic use, never published.

**Valid transitions (monotonicity constraint).** The synthesis worker and moderation system must enforce these and only these transitions:

| From | To | Permitted by |
|------|----|-------------|
| `pending` | `corroborating` | synthesis worker |
| `pending` | `expired` | synthesis worker (TTL) |
| `pending` | `disputed` | anti-spoof worker, moderator |
| `corroborating` | `confirmed` | synthesis worker |
| `corroborating` | `disputed` | anti-spoof worker, moderator |
| `corroborating` | `expired` | synthesis worker (TTL) |
| `confirmed` | `disputed` | moderator only |
| `disputed` | `confirmed` | moderator only |
| `disputed` | `expired` | moderator only |

Forbidden transitions that must be rejected at the database level via a trigger or in the worker via explicit guard: `expired → any`, `confirmed → pending`, `confirmed → corroborating`. These represent either a logic error or an injection attempt. The database trigger should log the attempted transition and raise an exception rather than silently ignoring it.

## Weighted Corroboration Scoring

Not all reporters count equally. The synthesis pipeline computes a weighted score for each candidate cluster.

### Reporter trust score (per pubkey, pre-computed, cached)

Score is a float in [0.0, 1.0]. Updated asynchronously by a background worker, never in the request path.

| Input | Weight | Notes |
|-------|--------|-------|
| Account age | 0.20 | Linear from 0 (new) to 1.0 (>180 days) |
| Successful detection history | 0.25 | Signals that contributed to later-confirmed events |
| Zap reputation | 0.15 | Normalised zap received volume |
| Proximity accuracy | 0.20 | Historical distance between claimed coords and cluster centroid |
| False positive history | −0.30 | Signals that were disputed or expired |
| Device integrity | 0.20 | Placeholder; 0.5 default until attestation implemented |

New accounts default to 0.40 until sufficient history is available.

### Trust decay and ceilings (Sybil maturity defence)

The trust score system is vulnerable to "slow farming": an attacker behaves honestly for weeks, accumulates reputation, then coordinates false incidents. This is the Sybil maturity problem. Three mechanisms limit it:

**Asymptotic growth ceiling.** Trust score growth rate slows as the score approaches 1.0. The effective increment per confirmed detection is `Δ = base_increment × (1 - current_score)`. A new account at 0.40 gains trust quickly; an account at 0.90 gains trust very slowly regardless of activity volume.

**Inactivity decay.** Trust scores decay toward 0.50 (not 0.0) at a rate of 0.01 per week of no confirmed contributions. An account built up over months and then unused for 3 months returns to near-baseline before it can be deployed. Decay is computed lazily at score-read time using `stored_score × decay_factor(weeks_idle)`.

**Nonlinear dispute penalty.** A disputed signal applies a penalty of `0.20 × current_score` (not a fixed subtraction). A high-trust account loses more from a dispute than a low-trust account. This makes reputation-farming costly to deploy: the attacker's most valuable asset is the most damaged by a single failed false incident.

**Trust ceiling for new accounts.** Accounts less than 30 days old cannot exceed trust score 0.60, regardless of activity. This prevents rapid farming via scripted corroboration loops.

**Anti-feedback-loop exploration weighting.** Reputation systems become self-reinforcing: high-trust accounts confirm more events, gain more history, maintain high trust. Low-trust accounts confirm fewer events, gain less history, stay low-trust. Without intervention this stratifies permanently. Add a small exploration floor: each signal's effective trust contribution is `max(trust_i, 0.15)` — meaning even a brand-new account contributes a small non-zero weight. This keeps low-trust accounts' evidence visible to the synthesis worker and allows trust to grow from genuine contributions. The floor is small enough that Sybil swarms cannot use it to inflate cluster scores past threshold.

### Cluster confidence score

```
cluster_score = Σ (trust_i × confidence_i)
                ──────────────────────────
                        Σ trust_i
```

The denominator is the sum of trust scores, not the count of contributors. Dividing by N would allow a swarm of low-trust accounts to dilute the score only weakly — many low-confidence submissions average up toward a passing score. Dividing by trust mass means a swarm of low-trust accounts contributes little to the numerator and dominates the denominator, driving the score toward zero. Sybil inflation fails because more low-trust accounts makes the score worse, not better.

Threshold to promote `corroborating` → `confirmed`: `cluster_score ≥ 0.60` with N ≥ 2 distinct pubkeys.

**Per-cluster trust contribution cap.** No single pubkey may contribute more than 25% of the total trust mass (`Σ trust_i`) in a cluster. If a pubkey's contribution would exceed the cap, its trust score is clamped to `0.25 × Σ trust_i` for this cluster's calculation only — the stored score is not modified. This prevents two failure modes: an elite-trust account unilaterally confirming an event, and a high-trust moderator-aligned account capturing the corroboration signal before independent voices can contribute.

CRITICAL-severity events require `cluster_score ≥ 0.75` with N ≥ 3 distinct pubkeys from at least 2 distinct device categories.

**Confidence uncertainty adjustment.** The cluster score is penalised when contributing signals show high internal disagreement:

```
adjusted_score = cluster_score × (1 - 0.5 × mean_confidence_variance)
```

`mean_confidence_variance` is the average of `confidence_variance` across contributing signals. A cluster where every signal has consistent confidence (variance ≈ 0) is unaffected. A cluster where signals show high frame-to-frame disagreement (variance ≈ 1) has its score halved. This prevents a brief loud transient — which produces a high-confidence spike followed by low-confidence frames — from scoring equivalently to a sustained, stable detection. The stored `cluster_score` in lineage is the raw value; `adjusted_score` is what determines promotion.

### Event confidence composition (multi-sensor)

When multiple sensor types contribute to the same spatial-temporal cluster:

```
event_confidence = 0.40 × acoustic_score
                 + 0.30 × crowd_report_score
                 + 0.20 × trusted_responder_score
                 + 0.10 × historical_hotspot_score
```

Weights are initial values, intended to be calibrated from outcome data. The composition formula is stored with each event for auditability.

## Spatial-Temporal Clustering Service

The synthesis pipeline runs as a background worker, not in the request path. It re-evaluates clusters on a 5-second tick for active windows.

### Algorithm

DBSCAN over H3 cells with temporal decay:

1. Group pending and corroborating signals by H3 r9 cell and `threat_class`.
2. For each group: compute pairwise H3 distance (k-ring neighbourhood ≤ 1 = same or adjacent cell).
3. Apply temporal decay: signals older than 60s contribute at 50% weight; older than 120s excluded.
4. If `cluster_score ≥ 0.60` and N ≥ 2 distinct pubkeys: promote all member signals to `corroborating`.
5. If `cluster_score ≥ 0.60` and promotion criteria met: create or update a `public_events` record; set trust state to `confirmed`.
6. Mark signals with no cluster match that are >5min old as `expired`.

For large incidents (cluster size > 50 signals within 5 minutes in a single H3 r7 cell):
- Aggregate to a single event record at r7 resolution rather than individual r9 markers.
- Broadcast a single aggregated WS message rather than per-signal updates.
- This is the emergency mode transition trigger.

### Cluster merge and split semantics

Real incidents evolve spatially and temporally. The synthesis worker must handle these deterministically:

**Merge.** Two confirmed clusters of the same `threat_class` within H3 k-ring distance ≤ 2 at r9, with temporal overlap < 120s, are candidates for merge. Merge condition: `cluster_score(combined) > max(cluster_score(A), cluster_score(B))`. On merge: create a new `public_events` record; set `status = 'merged'` on both source records; reference both source `event_id` values in the new record's lineage `derived_from`. Do not delete source records.

**Split.** A confirmed cluster whose contributing signals diverge spatially — centroid drift > 300m over 5 minutes — is a candidate for split. Split condition: DBSCAN produces two distinct density cores within the existing cluster boundary. On split: mark source event `status = 'split'`; create two new events referencing the source in lineage. Signal assignment follows the nearer density core.

**Severity evolution.** A `confirmed` event's severity may escalate (MEDIUM → HIGH → CRITICAL) as new contributing signals arrive and `adjusted_score` increases. Severity may not automatically downgrade — downgrade requires moderator action. Escalation is recorded in lineage as a new array entry.

All merge, split, and escalation decisions are idempotent: running the synthesis worker twice on the same input must produce the same output.

### Rolling threat score

Each H3 r7 cell maintains a rolling threat score: exponential moving average of confirmed event confidence over the past 24h, weighted by event severity. This feeds the `historical_hotspot_score` component in event confidence composition.

## Soft Visibility

Unconfirmed signals are not hidden entirely. They are shown as low-opacity "unverified acoustic activity" indicators, visible only to users within the same H3 r7 cell (approximately 5km radius).

Rules:
- `pending`: shown only to the submitting user on their own map view. Not broadcast.
- `corroborating`: shown at 20% opacity to users within H3 r7 cell. Labelled "unverified activity nearby."
- `confirmed`: shown at 100% opacity on global map.
- `disputed`: hidden from all views pending moderator decision.
- `expired`: not shown.

The viewport WS broadcast message includes a `trust_state` field. The PWA map layer uses opacity and label text based on this field. No separate endpoint is needed.

## Report UUID Deduplication

The client generates a UUIDv7 (`client_id`) before each submission. The server enforces uniqueness within a 10-minute sliding window via the partial unique index on `acoustic_signals`.

On duplicate: return 200 with `{ "deduplicated": true }`. Do not return 409 — the client should not retry on duplicate; it should treat the original submission as successful.

This deduplication is independent of NIP-98 replay protection. NIP-98 guards the transport (same HTTP request cannot be replayed). The `client_id` guards the payload (same detection cannot be submitted twice with a new signature).

## Anti-Spoofing Heuristics

Evaluated by the synthesis worker, not in the request path. Flagging a signal sets `trust_state = 'disputed'` and queues it for moderator review.

### Implemented at launch

**Impossible travel detection:** If the same pubkey submits signals from two locations more than 50km apart within 5 minutes, flag both signals as disputed.

**Synchronized burst detection:** If N ≥ 5 distinct pubkeys submit the same `threat_class` within the same H3 r9 cell within 10 seconds, apply elevated scrutiny: reduce automatic trust weighting for those signals by 30% and increase moderator queue priority. Do not auto-dispute the cluster. Real incidents — gunshots, explosions, crowd panic, alarms — naturally synchronize humans. Simultaneous detection is evidence of a real event, not evidence of coordination. Auto-disputing a synchronized burst during a genuine emergency would suppress the signal when it is most needed. Elevated scrutiny means the cluster requires moderator confirmation to reach `confirmed` state, but does not prevent it from reaching `corroborating` for soft visibility.

**Waveform fingerprint deduplication:** The client computes a sha256 of normalised waveform characteristics (spectral centroid, zero-crossing rate, RMS per band) and sends it as `signal_fingerprint`. If the same fingerprint appears from 3+ distinct pubkeys, it suggests a shared audio source or replay of a recorded sample. Flag for review.

### Deferred (post-launch)

- VPN/Tor risk scoring
- Device fingerprint anomaly detection
- Geographic entropy analysis (too-uniform distribution across many cells)
- Bot burst detection (submission timing variance)

## Adaptive Emergency Mode

Emergency mode activation is itself an attack surface. An attacker who can trigger emergency mode can raise corroboration thresholds and reduce broadcast frequency — effectively suppressing genuine signals during a real incident. The activation condition must be hard to fake.

Triggered when **all three** of the following are true in any H3 r7 cell within a 5-minute window:

1. **Trust-weighted signal density ≥ threshold.** `Σ trust_i` across all signals in the cell ≥ 15.0 (not raw signal count). A flood of low-trust signals cannot trigger emergency mode alone.
2. **Sensor diversity ≥ 2.** At least 2 distinct sensor types have contributed signals to the cell within the window. Acoustic-only floods cannot trigger emergency mode.
3. **Disputed ratio < 0.30.** Fewer than 30% of signals in the window are in `disputed` state. A coordinated burst that trips the synchronized-burst elevated-scrutiny flag will inflate the disputed ratio and prevent emergency mode activation.

If only condition 1 is met (high signal volume but single sensor, or high disputed ratio), the synthesis worker enters a **heightened monitoring state**: shorter tick interval (1s instead of 5s), moderator queue priority elevated, but thresholds and broadcast frequency are unchanged.

In emergency mode for affected cells:
- Corroboration threshold raised to N ≥ 3 (from N ≥ 2).
- Per-pubkey rate limit lowered to 2 signals/minute (from 5/minute).
- WS broadcast aggregates all signals in the cell to a single update per 10s tick.
- Server-side H3 r7 clustering applied; individual r9 markers not broadcast.
- Only CRITICAL and HIGH severity signals are broadcast.

Emergency mode exits when confirmed event count in the cell drops below 5 for 10 consecutive minutes.

## Acoustic Model Governance

Every signal record stores:

```json
{
  "model_version": "yamnet-tfjs-1",
  "threshold_profile": "default-v1",
  "inference_backend": "webgl",
  "processing_latency": 312,
  "dropped_frames": 0,
  "device_category": "mobile"
}
```

`threshold_profile` is a named, versioned configuration object (stored server-side) that maps threat class indices to per-class thresholds. This separates threshold calibration from model deployment — thresholds can be updated without a new app release by changing the active profile name.

The profile name is fetched from the API at session start. Default profile `"default-v1"` ships with the app as a fallback.

When a model version is found to have systematic errors, all signals tagged with that version can be reprocessed or batch-expired without affecting signals from other versions.

### Calibration replay tooling

The synthesis versioning in lineage (clustering algo, decay, trust weights, anti-spoof ruleset) exists primarily to enable this: reprocessing a historical window of `acoustic_signals` through a newer synthesis version to compare outcomes before deploying.

The replay pipeline reads from `acoustic_signals` with a time range filter, runs the synthesis worker against the selected records with a target version configuration, and writes results to a shadow table (`public_events_replay`) rather than `public_events`. Comparison metrics:

- False positive reduction: `disputed_ratio(replay) vs disputed_ratio(live)`
- Confirmation latency: median time from first signal to `confirmed` state
- Trust evolution: distribution shift in contributor trust scores
- Moderation outcome prediction: what fraction of moderator `dispute` actions would have been caught by anti-spoof rules in the new version

The replay pipeline is an offline tool, not a production service. It requires read access to `acoustic_signals` (exact coordinates available within the 24h retention window) and a separate database connection to the shadow table. It must not write to production tables.

The lineage `synthesis_version` and the individual algo/decay/trust/ruleset version fields make exact replay possible: given any historical event, you can reconstruct the exact synthesis configuration that produced it and diff it against any newer configuration.

## Human Moderation Escalation

### Triggers for moderator queue

- Anti-spoofing flag on any signal in a confirmed cluster.
- Single pubkey responsible for >40% of signals in a confirmed cluster.
- Manual report from a user disputing a map marker.
- Any CRITICAL-severity event (always queued, never auto-confirmed without moderator review at launch).

### Moderator actions

| Action | Effect |
|--------|--------|
| Confirm | Set `trust_state = 'confirmed'`; log moderator pubkey |
| Dispute | Set `trust_state = 'disputed'`; remove from map |
| Expire | Set `trust_state = 'expired'`; suppress for 24h |
| Lock | Prevent further signals from contributing to this cluster |
| Escalate to trusted responder | Notify via Nostr DM to responder pubkey list |

Moderator decisions are stored in an `acoustic_moderation_log` table with the moderator's pubkey and timestamp. Decisions are auditable and reversible.

### Incident locking

A locked incident accepts no new contributing signals. Used when an event is determined to be a false alarm to prevent continued corroboration from late-arriving signals.

### Moderation scalability

The current model — moderator reviews every CRITICAL event and every anti-spoof flag — does not scale. At meaningful user volume, the CRITICAL queue alone becomes a bottleneck, and moderation fatigue degrades review quality.

This spec does not solve scalability, but acknowledges it. Future evolution will require:

- Auto-expiration rules with SLAs: unflagged CRITICAL events older than N minutes without moderator action are automatically expired rather than staying in limbo.
- Trusted responder tier: a higher-trust class of users whose confirmation can substitute for a moderator action on non-CRITICAL events.
- Delegated regional moderation: moderators have jurisdiction over a geographic area, reducing queue size per moderator.
- Probabilistic moderation queues: not every anti-spoof flag requires human review; a confidence score on the flag determines whether it is auto-actioned, queued, or silently monitored.

These are out of scope for Phase 1–3. They must be designed before Phase 5 (reputation system) because the trusted responder tier feeds directly into the reputation weight for `trusted_responder_score`.

## Sensor Quorum Architecture

Long-term: no single sensor independently generates CRITICAL public alerts.

```
Sensor types:
  audio     — YAMNet acoustic detection (current)
  crowd     — manual user reports
  ble_mesh  — proximity anomaly from BLE circle members  [future]
  camera    — visual verification from trusted responder [future]
  responder — trusted responder confirmation             [future]
  iot       — environmental sensor feeds                 [future]
```

CRITICAL severity requires quorum: at least 2 distinct sensor types must independently corroborate within the same spatial-temporal cluster. A gunshot detection from audio alone cannot produce a CRITICAL marker; it requires either a crowd report, a trusted responder, or a BLE anomaly in the same area.

HIGH severity requires either quorum or a trusted responder confirmation. MEDIUM and LOW can be audio-only with cluster score ≥ 0.60.

The sensor quorum requirement is enforced by the synthesis pipeline, not by individual sensor ingest routes. Each sensor feeds its own staging table. The synthesis pipeline joins across sensor tables when computing cluster score.

### Sensor causal independence

Not all corroboration is independent. Two sensors that both react to the same public information are partially correlated, and treating them as independent evidence overstates certainty. The synthesis pipeline applies a causal independence weight when combining sensor contributions:

| Sensor pair | Independence | Notes |
|-------------|-------------|-------|
| Acoustic + BLE proximity anomaly | High (0.9) | Independent physical modalities |
| Acoustic + trusted responder (on-scene) | High (0.9) | Human direct observation |
| Acoustic + crowd reports (pre-public-alert) | Moderate (0.6) | Both from direct experience |
| Acoustic + crowd reports (post-public-alert) | Low (0.3) | Crowd reports may be influenced by seeing the alert |
| Acoustic + IoT environmental sensor | High (0.9) | Independent modality |
| Two acoustic signals from same H3 r9 cell | Low (0.4) | May share acoustic environment |

The adjusted multi-sensor confidence uses the independence weight as a discount on the secondary sensor's contribution:

```
multi_sensor_score = primary_score + independence_weight × secondary_score × (1 - primary_score)
```

This caps at 1.0 and ensures a low-independence secondary sensor provides diminishing marginal benefit. The independence weight and the formula version are stored in the event lineage.

## Privacy Invariants (ADR-001)

These are governance contracts, not implementation details. Any future feature that would violate them requires explicit architectural review and user consent.

**ADR-001: Acoustic Privacy Invariants**

1. Raw PCM audio never leaves the device. The AudioWorklet processes audio locally. Only derived signals (threat class, confidence, waveform fingerprint) are transmitted. Waveform fingerprints are not reversible to audio content.

2. No server-side audio storage. The gateway has no endpoint that accepts audio data. There is no audio upload path.

3. No background recording without explicit UI state. The microphone is active only when the acoustic detection session is explicitly started by the user and a visible UI indicator is active. There are no background activation paths.

4. No hidden microphone activation. The PWA does not request microphone access during app initialization. It requests permission only on explicit user action.

5. No biometric voice analysis. The YAMNet model classifies environmental sounds by category. It does not perform speaker identification, voice recognition, or any biometric analysis. The threat class set is restricted to the 10 environmental event classes defined in `acousticThreats.ts`. Adding voice-identification capabilities to the model or signal processing pipeline requires a separate ADR with explicit user consent flow.

6. Geolocation is transmitted only with detections. Location is not tracked continuously. `getCurrentPosition` is called only when a detection threshold is exceeded. The `maximumAge` parameter is set to 30 seconds to avoid unnecessary GPS activation.

Violations of these invariants — even partial, even in test environments — must be escalated to architectural review before merging.

### Coordinate precision degradation

H3 resolution 9 (~100m) is precise enough to reveal home address, workplace, and movement patterns from repeated submissions by the same pubkey, even without continuous tracking. A user who submits 10 signals from the same r9 cell over several weeks is effectively registering a location.

Exact coordinates and fine-grained cells are retained only transiently. A scheduled job (nightly) nulls columns on a rolling basis:

| Age | `lat`/`lng` | `h3_r9` | `h3_r7` |
|-----|-------------|---------|---------|
| < 24h | retained | retained | retained |
| 24h – 7d | nulled | retained | retained |
| > 7d | nulled | nulled | retained |

`h3_r7` (~5km²) is the permanent precision floor. It retains statistical value for hotspot analysis without enabling individual location inference. Synthesis worker and clustering algorithms use `h3_r9` during the active corroboration window (< 120s), at which point the cluster has already been resolved and fine precision is no longer needed.

## Observability

Required dashboards before production rollout:

### Ingest health
- `acoustic_signals` received per minute (by trust_state transition)
- Confirmation ratio: `confirmed / (pending + corroborating + confirmed)` over trailing 1h
- Per-class trigger distribution (which threat classes fire most)
- Dropped inference windows per device category
- Model load failures per hour

### Integrity health
- False positive ratio: `disputed / confirmed` over trailing 24h
- Pubkey reputation score distribution (P10, P50, P90)
- Geographic anomaly heatmap: signal density vs historical baseline
- Replay rejection count per hour (from NIP-98 replay guard)
- Anti-spoofing flag rate per trigger type

### Performance health
- Synthesis worker cycle time (P50, P95, P99)
- Cluster promotion latency: time from first signal to confirmed event
- WS broadcast latency at P95
- Redis PUBLISH lag from signal ingest to WS delivery

### Abuse signals
- Reports per minute from single pubkey
- Synchronized burst detection events per hour
- Impossible travel flags per hour
- Moderator queue depth

## Evidence Lineage

Every `public_events` record must carry immutable provenance back to its source signals, synthesis decisions, and any moderator actions. Without lineage, retroactive debugging, dispute review, and ML recalibration are all impossible — you can see the output but not reconstruct how it was produced.

### Schema additions to `public_events`

```sql
ALTER TABLE public_events ADD COLUMN lineage JSONB NOT NULL DEFAULT '{}';
```

The `lineage` column stores:

```json
{
  "derived_from": ["signal_uuid_1", "signal_uuid_2"],
  "merged_from": [],
  "split_from": null,

  "synthesis_version": "synth-v1",
  "synthesis_run_id": "uuid",
  "clustering_algo_version": "dbscan-h3-v1",
  "temporal_decay_version": "decay-v1",
  "trust_weight_version": "trust-v1",
  "antispoof_ruleset_version": "antispoof-v1",
  "sensor_independence_version": "indep-v1",

  "score_breakdown": {
    "acoustic": 0.72,
    "crowd": 0.00,
    "trusted_responder": 0.00,
    "historical_hotspot": 0.08
  },
  "cluster_score_raw": 0.73,
  "cluster_score_adjusted": 0.68,
  "confidence_variance_mean": 0.07,
  "threshold_profile": "default-v1",
  "n_contributors": 3,
  "trust_mass": 1.84,

  "moderator_actions": [
    {
      "action": "confirm",
      "moderator_pubkey": "...",
      "at": "2026-05-20T14:23:00Z"
    }
  ],
  "severity_escalations": []
}
```

The `lineage` column is append-only for array fields. The synthesis worker writes the initial snapshot at event creation. Moderator actions append to `moderator_actions`. Severity escalations append to `severity_escalations`. No array field is ever overwritten.

**Future migration to `event_lineage` table.** The JSONB append-only approach is correct conceptually and operationally sufficient for Phase 1–3. At scale it becomes expensive: large JSONB columns bloat table pages, JSONB updates require full-row rewrites, and querying `moderator_actions` requires GIN index or full-scan. When operational cost justifies it, migrate to:

```sql
CREATE TABLE event_lineage (
    id           BIGSERIAL PRIMARY KEY,    -- sequence ordered, immutable
    event_id     UUID NOT NULL REFERENCES public_events(id),
    entry_type   TEXT NOT NULL,            -- 'synthesis' | 'moderator_action' | 'severity_escalation' | 'merge' | 'split'
    payload      JSONB NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON event_lineage (event_id, id);
```

Each row is immutable. The full event history is the ordered sequence of rows for an `event_id`. The `lineage` JSONB column on `public_events` becomes a denormalized cache of the latest synthesis snapshot for fast reads; `event_lineage` is the authoritative record. This migration does not require downtime — the two representations can coexist during transition.

### Why this matters

- **Forensic reconstruction:** Given a disputed event, you can replay exactly what signals contributed, what scores they had, and which synthesis version ran.
- **Retroactive recalibration:** If a model version is found to have systematic errors, all events with `lineage->>'synthesis_version' = 'synth-v1'` and `lineage->'score_breakdown'->>'acoustic' > '0.5'` can be batch-reprocessed.
- **ML evaluation:** Ground-truth labels (disputes, moderator confirmations) can be joined back to signals via `derived_from` UUIDs for training data.
- **Trust transparency:** A user disputing a map marker can see the score breakdown and signal count that produced it, without exposing individual reporter identities.

## Phased Implementation Order

This architecture is too large to implement in a single PR stream. Debugging becomes nearly impossible when reputation, clustering, anti-spoofing, and moderation are all in flight simultaneously. Each phase must be stable and observable before the next begins.

### Phase 1 — Secure ingest
NIP-98 auth on acoustic ingest, `client_id` UUIDv7 deduplication, per-pubkey rate limits, `acoustic_signals` table, server-side H3 derivation, remove direct public event creation from the acoustic path. ADR-001 enforcement as a review checklist item.

**Exit criterion:** Acoustic signals are stored, authenticated, deduplicated, rate-limited, and never touch `public_events` directly.

### Phase 2 — Signal staging and soft visibility
Trust state machine (`pending` → `corroborating` → `confirmed` → `disputed` → `expired`), WS broadcast carries `trust_state`, map layer renders soft visibility per state, per-class cooldown in PWA, `visibilitychange` lifecycle stop.

**Exit criterion:** Unconfirmed signals are visible locally at low opacity; confirmed signals are visible globally; disputed signals are hidden; states transition correctly.

### Phase 3 — Synthesis worker
DBSCAN/H3 clustering, trust-mass-weighted scoring formula, temporal decay, cluster promotion, rolling threat score, evidence lineage written to `public_events`. No reputation system yet — all trust scores are default (0.40).

**Exit criterion:** Clusters form, score, and promote correctly under load. Lineage records are complete and queryable. Observable via the synthesis worker cycle time dashboard.

### Phase 4 — Anti-spoofing
Impossible travel detection, waveform fingerprint deduplication, synchronized burst elevated-scrutiny (not auto-dispute). Moderation queue integration.

**Exit criterion:** All three heuristics fire correctly in abuse simulation tests without suppressing genuine incident clusters.

### Phase 5 — Reputation system
Trust scoring, history weighting, inactivity decay, asymptotic ceiling, dispute penalty, 30-day new-account ceiling. Requires Phase 3 data (confirmed event history) for meaningful inputs.

**Exit criterion:** Trust scores diverge meaningfully between honest long-term users and new accounts. Farming simulation (scripted corroboration loop) does not produce high trust within a 7-day window.

### Phase 6 — Multi-sensor synthesis
Crowd reports feed into the composite confidence formula alongside acoustic. Responder tier confirmation. Sensor quorum enforcement for CRITICAL severity.

**Exit criterion:** CRITICAL events require multi-sensor corroboration. Single-sensor acoustic alone cannot produce a CRITICAL marker.

## What This Does Not Change

- The NIP-98 authentication implementation (PR #33) is unchanged. The `acoustic_signals` ingest route uses `NostrAuth` exactly as specified there.
- Existing `reports` table and `POST /api/reports` route remain. This spec introduces `acoustic_signals` as a new parallel ingest path. Migration of the acoustic flow away from `reports` is a separate task.
- The YAMNet inference logic in the PWA is unchanged by this spec. Changes to threshold profiles and class lists are governed by this spec but implemented in a separate plan.
